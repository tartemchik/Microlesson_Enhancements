AI Literacy Microlessons · Platform Enhancements · E1
Tabbed Scenario Switcher
Requirements & Alternatives
Audience-lens navigation for the layered example pattern · Modules 2–4
Enhancement E1 High Priority 4 Alternatives Evaluated Full Requirements Included
Context
Why this enhancement is needed

All three new modules (2, 3, and 4) use a layered example pattern: every concept is illustrated through three parallel life-context lenses — Student, Job Seeker, and Everyday Life. The platform currently has no way to present three parallel content variants and let learners switch between them. The current workaround is three stacked Show/Hide sections, which has real limitations at scale.

The gap
Three stacked Show/Hide sections require learners to scroll past content that doesn't apply to them. There's no visual signal that they're making a choice between equivalent options — the interaction implies all three should be read, not that one is theirs. As modules expand, pages with 6–7 audience-segmented sections become unwieldy.
Design principle
The three lenses are mutually exclusive audience contexts, not sequential steps or hierarchical information. A learner belongs to one context and should be able to navigate directly to their scenario without interacting with the others at all. Tabs are the correct interaction pattern for this structure.

A
Separate Pages via Sidebar Navigation
Split scenarios across separate lesson pages; use existing sidebar nav to jump between them
Zero dev cost
How it works: Each scenario (Student, Job Seeker, Everyday Life) lives on its own lesson page. Learners use the sidebar page list to navigate directly to the page relevant to them. No new platform functionality required.
Works for
  • Zero development cost
  • Works with all existing platform constraints
  • Sidebar already supports labeled page navigation
Drawbacks
  • No choice signal — learners don't know they're selecting their context
  • Requires page navigation rather than in-place switching
  • Inflates lesson page count across all modules
  • Learners who don't read the sidebar labels won't know options exist

C
Button-Reveal Panel (Tab Variant)
Three side-by-side audience buttons; clicking one reveals that scenario's content directly below — implemented as a visual variant of the tab component
Medium dev cost Recommended near-term
How it works: Three equal-width button cards sit side by side, each labeled with an audience lens (Student, Job Seeker, Everyday Life). Clicking one activates it (highlighted state) and reveals that scenario's content in a panel directly below all three buttons. Clicking a different button swaps the content. Only one panel is visible at a time. Implemented as a visual variant of the tab component (Option E) — same underlying interaction logic, same ARIA pattern, different visual treatment. Framing it as a variant reduces dev cost significantly vs. building two separate components.
Works for
  • Strong audience-choice signal — three equal options, none implying sequence
  • Content appears below selection — spatial logic matches mental model
  • Button card format is visually richer than a tab bar
  • Shares component logic with Option E — lower marginal dev cost if E is also built
  • Accessible — same ARIA tab pattern applies
Drawbacks
  • Medium dev cost — requires new visual treatment even if tab logic is reused
  • Questions still cannot live inside panels (E2 dependency, same as Option E)
  • Three-column layout may be tight on mobile viewports

D
Audience Selection Landing Page
Learner selects their context on a dedicated intro page; selection influences content display on the following page
Medium dev cost
How it works: Before the scenario page, a dedicated page presents three labeled buttons. The learner selects their context. A session variable stores the selection and either pre-expands or highlights the relevant Show/Hide section on the next page. The selection moment is intentional and explicit — the design communicates "this content is for you" rather than leaving discovery to the learner. However: this approach requires session state storage and conditional display logic, which may be more complex than tabs depending on platform architecture.
Works for
  • Strongest "this is yours" moment — explicit choice upfront
  • Could scale to personalize content across multiple pages
  • Selection UI is highly flexible and branded
Drawbacks
  • Adds a page to every lesson that uses layered examples
  • Requires session state — potentially more dev work than tabs
  • Learner can't change their mind without going back
  • Overkill for a single practice page; better suited to full personalization feature

E
True Tab Component (New Development)
A native tab bar component that switches content panels in place — the correct UX pattern for parallel, mutually exclusive content
Higher dev cost Full requirement below
How it works: A horizontal row of labeled tab buttons. Each tab controls a content panel. Clicking a tab hides all other panels and shows the selected one. Active tab is visually distinguished. Works exactly as tabs work across the web — no new UX paradigm for learners to learn. Correct semantic HTML with full ARIA support.
Works for
  • Correct interaction pattern — universally understood
  • True audience-choice signal — not a sequential pattern
  • Extensible to 4–5 lenses as modules grow
  • Fully accessible with ARIA tab pattern
  • Consistent with web standards learners already know
Drawbacks
  • Higher development cost than other options
  • Questions still can't live inside panels (E2 dependency)
  • Requires new component in platform component library

Recommendation
Near-term (FY2027 launch): Implement Option C — the button-reveal panel as a visual variant of the tab component. Framing it as a variant of Option E reduces the total dev cost of building both, since the interaction logic is shared. The button card format gives a stronger audience-choice signal than a tab bar and the content-below-selection spatial logic is intuitive. Long-term: Option E (tab bar) complements Option C as a second visual treatment — useful for content contexts where a horizontal tab bar is more appropriate than a full-width button grid.
Part 2
E1 Full Requirements — Tab Component
Scope
These requirements define the full Tab component for Option E. They are intended for product and engineering review and serve as the acceptance criteria for development. Option C (Carousel extension) requires a lighter-touch spec and is not covered here.
Rendering & Layout
Requirement IDDescription
FR-E1-01 The tab bar renders as a horizontal row of labeled buttons directly above the content region it controls. Minimum 2 tabs, maximum 5 tabs per tab group. Tab labels are specified by the content author and may include a single leading emoji or icon.
FR-E1-02 The tab bar sits on a 2px Rule Blue (#D1D8E8) bottom border spanning the full container width. The active tab's 3px Coral (#F76C6C) bottom border overlaps this to create a visual "selected" tab state. Inactive tabs have no bottom border.
FR-E1-03 Active tab styling: Coral (#F76C6C) label color, font-weight 700, 3px Coral bottom border. Inactive tab styling: Slate Blue (#6B7FA3) label color, font-weight 600, no bottom border. Hover state on inactive tabs: Navy (#374785) label color. Transitions on color: 150ms.
FR-E1-04 On page load, Tab 1 is active and its panel is visible. All other panels are hidden (display: none or equivalent). Default active tab may optionally be overridden by content author via storyboard notation.
Interaction Behavior
Requirement IDDescription
FR-E1-05 Clicking an inactive tab: hides the currently visible panel, shows the newly selected panel, updates active state styling on the tab bar. Panel switching must be instantaneous — no transition animation on the panel itself.
FR-E1-06 Content within panels must retain its expanded/collapsed state when switching tabs. A Show/Hide section that was open in Tab 1 remains open when the learner switches away and returns to Tab 1 within the same page session.
FR-E1-07 Tab selection is not persisted across page reloads or lesson sessions. Each new page load starts with Tab 1 active.
FR-E1-08 Clicking the currently active tab does nothing — no toggle, no collapse, no state change.
Content Within Panels
Requirement IDDescription
FR-E1-09 Tab panels may contain any standard platform content type: body text, callouts (all types), Show/Hide sections, images, AI Output cards, annotation tables, verdict cards, and Real Talk callouts.
FR-E1-10 Tab panels may not contain nested tab groups. One level of tabbing only.
FR-E1-11 Knowledge check questions (multiple-choice, multiple-select, drag-and-drop, and all other question types) may not be placed inside tab panels in v1. This is a known content constraint; see E2 for the dependency that would enable this in a future release.
FR-E1-12 All tabs must have content. Empty panels are not permitted. The authoring system should surface a validation error if a tab is defined without associated panel content.
FR-E1-13 Maximum one tab group per lesson page. Multiple tab groups on the same page are not supported in v1.
Responsive Behavior
Requirement IDDescription
FR-E1-14 On viewports narrower than 480px where tab labels overflow the container width, tabs must either wrap to a second row or convert to a select/dropdown menu. Horizontal scrolling within the tab bar is not acceptable.
FR-E1-15 Tab labels must not truncate at any viewport width. If a label would truncate, the responsive behavior in FR-E1-14 must activate before truncation occurs.
Accessibility
Requirement IDDescription
FR-E1-16 Tab bar must implement the ARIA tabs pattern: role="tablist" on the container, role="tab" on each button, role="tabpanel" on each panel.
FR-E1-17 Each tab must carry aria-selected="true" when active and aria-selected="false" when inactive. Each tab must have an aria-controls attribute linking it to its panel ID.
FR-E1-18 Keyboard navigation must follow the ARIA tabs pattern: Left/Right arrow keys move focus between tabs within the tablist. Enter or Space activates the focused tab. Tab key moves focus into the active panel content (not to the next tab button).
FR-E1-19 On tab activation, focus must move to the newly visible panel (or to the panel's first focusable element) so keyboard and screen reader users receive the same context switch as mouse users.
Authoring & Storyboard Notation

Content authors specify a tab group using the following prod note and manuscript conventions:

// Prod note at the point where the tab group begins: Tab Group (Student | Job Seeker | Everyday Life; default: Tab 1) // Panel content uses delimiter tags: [Tab: Student] ... all content for the Student panel ... [/Tab] [Tab: Job Seeker] ... all content for the Job Seeker panel ... [/Tab] [Tab: Everyday Life] ... all content for the Everyday Life panel ... [/Tab] // Standard content types within panels use existing manuscript format. // Audience lens tags on Show/Hide triggers within panels are optional // (the tab label already signals context).
Requirement IDDescription
FR-E1-20 The authoring system must validate that: (a) each Tab Group has between 2 and 5 tabs, (b) every tab has a corresponding panel with content, (c) no tab group is nested inside another, (d) no knowledge check questions appear inside panels.
FR-E1-21 Tab labels are plain text strings of 1–3 words. A single leading emoji is permitted. No HTML or rich text formatting in tab labels.
